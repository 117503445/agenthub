# 需求

## 产品范围

- 项目只需要 Web 前端，不需要 Android 或其他客户端。
- 前端内嵌到 Go 后端中，不需要独立部署。
- 不使用 Connect RPC，只使用 `github.com/coder/websocket`。
- 前端直接通过 `/ws` 相对路径连接后端，不需要 `direct`、`relay`，也不需要一个前端连接多个后端。
- 第一版不需要文件变更列表、Git 等额外功能。
- 部分技术实现可以参考 `/workspace/project/paseo`。

## 参考与风格

- 前端设计、配色、样式参考 `/workspace/project/paseo`，以 paseo 为主。
- 可以访问 `app.paseo.sh`，输入 `localhost:6767`，体验 paseo 的前端交互。
- 同时参考 `ui-ux-pro-max`。
- 前端需要参考 `/workspace/project/open-design` 的 skill 工作流和 Material Design 主题重构，保留工作台效率优先的信息结构。
- Material 主题不使用紫色主色，改用更中性的蓝色主色。
- 聊天页的 Tab 参考 `https://ui.shadcn.com/docs/components/base/tabs`。
- 尽量改造为 shadcn 组件。
- 文案尽量简约。
- 滚动条使用 paseo 风格。
- 项目使用浅色 Tabler `chart-bubble` 图标作为 AgentHub 图标，并作为浏览器 favicon 加载。

## Project 管理

- 支持 Project 列表的增删改查。
- 新建 Project 时不需要输入 Project 的 `name`。
- 左下角加号用于弹出工作目录输入框，不常驻显示“新建 Project / 工作目录”表单。
- 侧边栏只显示 Project 路径最后一个文件夹的名字。
- Project 列表项不显示编辑按钮，删除按钮和 Project 名称在同一行。
- 新建 Project 后自动打开一个聊天页。
- 后端启动时，如果进程工作目录是 Git 仓库，自动添加该 workdir 为 Project，并自动创建首个聊天页。
- 选中 Project 后，可以新建多个聊天页。
- 切换 Project 时需要记住每个 Project 最近选中的聊天页；再次切回该 Project 时，自动恢复到对应聊天页。
- 顶端显示当前 Project 的完整路径和 Git 信息。
- Git 信息和 Project 完整路径显示在同一行，Git 哈希不重复显示。
- 左上角只显示后端机器名和连接状态，并放在一行，不显示 “AgentHub Projects”。
- 项目命名统一使用 AgentHub 或 agenthub，不保留旧命名。
- 左下角显示添加 Project 和设置入口。
- Project 列表项需要展示聊天页聚合状态：工作中为黄色圆点，失败为红色圆点，成功为绿色圆点。
- Project 列表支持拖拽调整顺序，调整后的顺序需要由后端保存；新增 Project 默认显示在列表最上面。

## 聊天页

- 每个聊天页是一个 Tab。
- 每个聊天页的聊天输入草稿互相独立，切换 Tab 时保留当前 Tab 未发送内容，不带到其他 Tab。
- 每个聊天页未发送的输入框文字草稿需要保存到后端，刷新或重新打开前端后从后端恢复。
- 切换聊天页后再切回时，保留该聊天页之前的滚动位置；如果离开期间该聊天页有新的 agent 输出，再切回时自动滚动到底部。滚动位置只保存在前端内存中，不做前端或后端持久化。
- 每个聊天页第一次发送 Prompt 后，Tab 标题需要显示这次聊天的主题，主题从首次 Prompt 派生并在刷新后保留。
- 每个 Tab 占据完整高度。
- Tab 高度和文字大小参考 paseo，保持紧凑，并显示关闭叉叉图标。
- 聊天页 Tab 需要展示状态：工作中为黄色圆点，失败为红色圆点，成功为绿色圆点；用户在该聊天页进行任意点击操作后清除绿色或红色圆点。
- 最右侧 Tab 的右边有加号图标，用于新建聊天页。
- 没有聊天内容时，可以在聊天框下方选择 Agent、模型和思考深度。
- 每个聊天框第一次选择 Agent 后，后续聊天不能更换 Agent。
- 聊过一次以后，仍然可以更换模型和思考深度。
- 模型选择和思考深度设置都放在聊天框下面。
- 聊天框中的 Agent、模型和思考深度选择样式参考 paseo，保持简洁美观。
- 聊天框中的 Agent、模型和思考深度选择框宽度需要根据实际选项内容调整，不使用固定宽度。
- 聊天输入框参考 paseo：居中圆角矩形，不占据整个宽度；初始高度较小，输入内容增多后自动增高并有高度上限；Agent 选择、模型选择和推理级别选择放在输入框内部。
- 聊天输入框外的任务栏区域背景需要和聊天页背景一致，使用 `bg-[var(--agenthub-bg)]`。
- 聊天输入框输入 `/` 时展示可选 skills，选择后把对应 `/skill-name ` 插入输入框，交互参考 paseo。
- skills 菜单支持键盘上下键切换选中项，并可用 Enter 或 Tab 确认插入。
- 每次用户在聊天输入框输入 `/` 时，前端请求后端重新扫描最新 skills。
- 后端刷新 skills 后，如果结果和上一次不同，打印包含 skills 列表的日志，并向前端推送更新。
- 聊天输入框需要显示 context window 使用情况图标，样式和信息密度参考 paseo。
- context window 使用情况只能使用 agent 真实上报数据，不使用前后端本地估算。
- 如果当前聊天始终没有 agent 真实上报 context window 数据，不显示 context window 图标。
- 如果 agent 真实上报的 context window 用量低于 1/4，不显示 context window 图标。
- 聊天输入框左下角加号支持选择本地图片作为附件。
- 聊天输入框左下角添加图片按钮使用图片 logo。
- 聊天输入框支持直接 `Ctrl+V` 粘贴剪贴板图片作为附件。
- 图片附件需要在发送前展示预览，并随消息一起提交给 agent。
- 发送后的用户消息需要展示已提交的图片附件。
- 输入框和聊天正文使用 16px 字号。
- 聊天框不显示“Agent”标签和“已锁定”文字。
- 用户输入文字后，才在右下角显示发送图标。
- 用户提交聊天输入后，发送按钮立即进入转圈状态；发送失败时展示错误并恢复为发送按钮；发送成功后聊天页立即滚动到底部。
- 聊天页任务栏固定在页面最下面。
- 右上角不显示当前 Agent。
- 没有消息时不显示“还没有消息”空状态。
- 不显示“创建聊天后开始”空状态。
- AI 回复尝试使用 Markdown 渲染。
- AI 回复 Markdown 中带续行或空行的有序列表需要保持连续编号，不能渲染成多个 `1.`。
- AI 回复 Markdown 中的文件路径链接需要通过后端文件系统 API 打开；绝对路径直接使用，相对路径按当前 Project 根目录拼接。
- AI 回复 Markdown 中的文件路径链接如果带有行号后缀，例如 `path/to/file.go:68`，应打开去掉行号后的真实文件，不能因为行号后缀返回 `file not found`。
- 复制 AI 回复时保留 agent 返回的原始 Markdown，不复制展示层改写后的文件系统 API 地址。
- 聊天消息不显示“你”或 Agent 名称等角色名，直接展示内容。
- 聊天消息时间精确到秒；用户输入内容的时间显示在消息框外右上角，Agent 输出内容的时间显示在消息内容外左上角。
- 用户发送记录鼠标悬停时在消息框外右下角显示复制按钮；Agent 回复左下角始终显示复制按钮。
- 用户第一次输入 Prompt 时，后端初始化一个 Agent 进程，并把 Prompt 传给 Agent。
- 后端需要流式转发 Agent 的返回结果给前端。
- Agent 正在输出时，发送按钮变成停止按钮。
- Agent 输出完成后，停止按钮重新变成发送按钮。
- 用户可以主动点击停止按钮停止 Agent 输出。
- Agent 输出完成或用户停止后，用户可以继续输入 Prompt。
- 用户也可以在不点击停止的情况下直接输入并回车，行为等同于先停止当前输出，再发送新的消息。
- 输出和工具调用需要像 paseo 一样按发生顺序交替显示。
- 不允许把所有输出集中在最上面、所有工具调用集中在下面。
- 新建聊天默认使用上一次聊天选择的 agent、模型和思考深度。

## Plan 模式

- 聊天框提供 plan 模式开关，交互参考 paseo。
- 开启 plan 模式后，agent 只生成计划和待确认意见，不直接执行实现。
- 用户可以继续回复每一条待确认意见，让 agent 修订 plan。
- 生成 plan 后，前端需要展示 plan 卡片。
- 用户可以在 plan 卡片上点击开始执行，后端用已确认 plan 启动执行模式。
- Mock Codex 和 Mock Claude Code 都需要在 mock 模型服务下跑通完整 plan 流程：生成 plan、根据用户回复修订 plan、点击开始执行后进入执行阶段。
- Mock 模型服务需要根据 plan 阶段返回稳定内容，避免 mock agent 因通用回显或工具调用提前进入实现。

## 桌面通知

- agent 完成回复后，前端发送桌面通知。
- 用户手动停止 agent 输出时，不发送桌面通知。
- 浏览器支持通知权限时，需要在用户发送消息的交互中请求授权。

## 后端状态

- 所有状态由后端维护。
- 后端保存上一次选择的 agent、模型和思考深度，并在状态快照中返回。
- 即使关闭前端网页，会话仍然继续。
- 重新打开前端网页后，仍然能看到后端继续把 Agent 输出流式返回给前端。
- 报错时需要把错误信息返回到前端。
- 添加 `AGENTHUB_DATA` 环境变量，默认值为 `~/.agenthub/data`。
- 同一个 `AGENTHUB_DATA` 同时只能有一个后端进程使用；后续进程启动时如果检测到已有进程仍存活，则自行退出。
- 后端状态使用 JSON 文件存储在 `AGENTHUB_DATA` 下。
- 启动时从 `AGENTHUB_DATA` 读取状态到内存；后续每个写入操作先写入 JSON，成功后再更新内存状态。
- 启动加载时无法恢复正在运行的 agent 子进程，旧的运行中聊天需要标记为已停止。

## Agent 类型

- Agent 分为四类：
  - Claude Code。
  - Codex。
  - Mock Claude Code。
  - Mock Codex。
- 只有启用 `MOCK_AGENT` 时，才展示 Mock Claude Code 和 Mock Codex 的内置 profile；默认启动只展示真实 Claude Code 和 Codex。
- `MOCK_AGENT` 只控制 mock profile 是否出现在产品中，不用于判断真实 Claude Code 或 Codex 的登录状态。
- Mock Agent 必须跑通：
  - Mock Claude Code 要实际调用 `claude`，但请求打到后端 Mock Claude 模型服务。
  - Mock Codex 要实际调用 `codex`，但请求打到后端 Mock Codex 模型服务。
- 选择 Mock Claude Code 或 Mock Codex 时，后端必须按当前服务端口强制注入本机 mock 服务地址，不能因为用户本机真实 CLI 登录态或 API Key 而打到外部服务。
- E2E 中不要使用真实的 Codex 和 Claude Code。
- E2E 中需要有 Mock Codex 和 Mock Claude，二者各自指向服务端 Mock 模型服务。
- 后端需要提供 Anthropic 兼容的 Mock 服务，便于测试 Claude Code。
- Claude Code 启动命令为 `IS_SANDBOX=1 claude --dangerously-skip-permissions`。
- Codex 启动命令为 `codex --dangerously-bypass-approvals-and-sandbox`。
- Codex 需要真实可用，并支持选择 `gpt-5.5`。
- Codex resume 后继续发送以 `--` 开头的 prompt 时，需要作为普通用户输入传递，不能被 Codex CLI 解析成命令参数。
- Codex 使用 `gpt-5.5` 时需要支持思考深度选择：
  - Low：Fast responses with lighter reasoning。
  - Medium：Balances speed and reasoning depth for everyday tasks，默认值。
  - High：Greater reasoning depth for complex problems。
  - Extra high：Extra high reasoning depth for complex problems。
- 需要跑通 Codex 当前拿不到返回结果的问题。

## Agent Profile 管理

- Agent 以 Profile 为维度管理；一个 Profile 表示一套可启动 agent 的运行配置。
- Profile 动态配置包含模型列表，模型项用于聊天中动态切换，并支持增删改查。
- Profile 模型列表支持在设置页切换默认模型。
- 模型项不区分展示名称和标识，界面和后端统一使用同一个模型值。
- Profile 静态配置包含类型、命令、固定参数和环境变量。
- Profile 类型包括 `codex` 和 `claude_code`；Mock Claude Code 和 Mock Codex 只在启用 `MOCK_AGENT` 时作为内置 profile 出现。
- Mock Claude Code 和 Mock Codex 与普通 Profile 走同一套启动逻辑，只是 endpoint 指向后端 localhost mock 服务。
- 后端需要展示启动时的环境变量。
- 实际调用 agent 的环境变量为后端启动环境变量叠加 Profile 环境变量。
- Profile 环境变量覆盖同名后端环境变量。
- Profile 环境变量需要支持 unset 某个后端环境变量。
- Effective Env 允许用户查看完整密钥。
- 第一次初始化数据目录时自动探测环境，添加内置 Profile。
- 不根据 `ANTHROPIC_API_KEY` 或 `OPENAI_API_KEY` 判断 Profile 是否可用；订阅登录等方式可能不需要 API Key。
- 内置 Profile 可以编辑和删除。
- 不需要恢复默认按钮；出问题时删除旧 Profile 后重新添加内置 Profile。
- 不管之前的内置 Profile 是否删除过，都可以再次添加新的内置 Profile。
- 每个聊天框第一次发送消息后绑定一个 Profile agent 进程，之后不能切换 Profile。
- 聊天开始后仍允许在当前 Profile 的模型列表中切换模型，切换影响后续消息。

## 启动配置

- 后端读取 `AGENTHUB_PORT`、`AGENTHUB_LOG_NO_COLOR`、`AGENTHUB_TOKEN` 和 `AGENTHUB_DATA` 等应用环境变量。
- `AGENTHUB_PORT` 配置 Web 服务监听端口，默认使用更独特的 `17375`，也可通过 Kong CLI 的 `--port` 参数覆盖。
- `AGENTHUB_LOG_NO_COLOR` 用于禁用日志颜色，只通过环境变量生效，并在 Kong CLI 帮助信息中隐藏。
- `AGENTHUB_TOKEN` 默认为空；非空时前端必须先输入匹配 token 才能使用，也可通过 Kong CLI 的 `--token` 参数覆盖。
- `AGENTHUB_DATA` 配置后端 JSON 状态目录，默认 `~/.agenthub/data`。
- `AGENTHUB_MOCK_CLAUDE_COMMAND` 和 `AGENTHUB_MOCK_CODEX_COMMAND` 仅用于 E2E 覆盖 Mock Agent 命令，默认仍为 `claude` 和 `codex`。
- 前端需要储存的唯一状态是 `AGENTHUB_TOKEN`。

## 技术约束

- 前端使用 TypeScript 编写。

## 发布流水线

- 每个 push commit 都触发 GitHub Actions 发布流程。
- 发布流程需要通过 Docker build 构建，构建方式参考 `scripts/docker/web.Dockerfile`。
- 发布流程需要启用 GitHub Docker build cache。
- 生成 Linux 和 macOS 的 x86、arm 二进制产物，并发布到 GitHub Release；不编译 Windows 产物。
- 将 Linux 二进制放入 Alpine 镜像，并发布 amd64、arm64 双架构镜像到 GHCR。
- Release 需要附带 `install.sh`，该脚本默认从最新 master 对应的 GitHub Release 下载当前系统架构的二进制并安装。
- README 需要说明如何使用 `install.sh` 安装。
- 每次 CI 都需要运行 E2E。
- E2E 测试报告需要上传到 workflow artifacts，并在 Workflow Summary 中展示本次测试概要。
- E2E 测试报告需要发布到 GitHub Pages，每个 commit 的报告都能在独立页面查看。
- E2E 环境需要通过 Docker build with cache 构建镜像，并通过运行该 Docker 镜像执行 E2E 和输出报告。
